调用者 -> 条件分支: `src/gateway/client.zig:1825-1844` 在有连接时启动 `spawn_gateway_cancel_watcher()`，watcher 在 `src/gateway/client.zig:2406-2416` 检测 caller deadline，先调用 `win_deadline()` 再 `stream.shutdown()`。Windows 可达: `stream.shutdown` 走 std `Io.Threaded.netShutdownWindows` 的 AFD `PARTIAL_DISCONNECT`；没有 `os.tag` 排除。失败 fallback: `finish_error()` 把 `.timed_out` 映射为 `error.Timeout`，优先于读返回的 `Unexpected`。反证与排除: `git --no-pager diff 798c71f..0b6f2d` 显示基线无 `win_deadline`，新提交新增该状态和三个适配器顺序修复；`main.zig` 只关闭生产构建 std 的 Unexpected trace，测试仍保留。新问题: `isTransientTransportError()` 对 `Unexpected` 没有来源门限，测试使用 `FakeStream`，没有 Windows AFD 或 `std.Io.Threaded` 条件测试；权限 reviewer 与 gateway 主路径的重试集合仍不完全相同。可信度: 代码证据高；Windows 实机行为为中，用户提交说明与本机问题复现支持该机制，但本审查未构建或运行 Windows 网络回归。

### W-NA-03：TLS 后端、证书与代理

调用者 -> 条件分支: `HttpPool.init()` 构造 `std.http.Client`，`client.request()` 的 TLS preamble 调用 `Certificate.Bundle.rescan()`；`http_pool.ensureTlsReady()` 为直接 `client.connect()` 重复同一 preamble。Windows 可达: std `Bundle.rescan` 的 `.windows` 分支进入 `rescanWindows`，用 `CertOpenSystemStoreW(..., "ROOT")` 枚举证书；`std.crypto.tls.Client.init` 使用这个 bundle。反证与排除: 全仓库 `grep` 无 `initDefaultProxies` 调用、无 `http_proxy =`/`https_proxy =` 赋值、无 `NO_PROXY`、无 WinHTTP 或系统代理注册表；std 的 `initDefaultProxies` 是公开函数但无 caller。环境变量大小写: Windows `std.process.Environ.Map` 的 hash/eql 忽略大小写，但产品根本没有读取这些键。自签证书: 只有进入 Windows ROOT 系统存储或通过 web fetch 自行扩展 bundle 才可能信任；仓库无 `SSL_CERT_FILE` 等变量。可信度: 代码证据高。

### W-NA-04 与 W-NA-18：后台 HTTP GET 与 probe

调用者 -> 条件分支: `main.zig:775-781` 与 `cli_ask.zig:1566-1582` 调用 `HttpPool.warmAsync()`；该函数在非 test build 用 `std.Thread.spawn` 并 detach。Windows 可达: native process 在 `main.zig:4045-4075` 安装 `std.Io.Threaded`，`io_mod.getIo()` 是 warm 线程实际使用的 Io。反证与排除: `git show 401e17c3` 的提交说明指出早期 hang 来自探针 `Thread.yield()` 饿死 worker，撤回「threaded Io broken」结论；`build.zig` 的 `probe-http` 只在显式 step 中运行，不挂载到默认 build/test。残留问题: `warm()` 没有 deadline/cancel，`deinit()` 等 500 ms 后可能放弃 pool；该结论是静态推断，未实机复现。可信度: 历史结论为 git 证据高；残留生命周期风险为静态推断中高。

### W-NA-05、W-NA-06、W-NA-07：SSE、升级下载与 web fetch

调用者 -> 条件分支: gateway stream 在 `client.zig:1825-1844` 启动 cancel watcher，SSE reader 在 `sse.zig:101-129` 检查 cancel flag；`runBoundedHttpOperation` 用 `std.Io.Select` 让 operation 与 watch 竞速。Windows 可达: watcher 的 `stream.shutdown` 在 std Windows 分支有 AFD 实现，新提交把 deadline 记为终止原因。失败 fallback: Windows 无 dead-peer probes、无 local-address watch，只能等 stall/deadline；`validateApiKey` 使用不带 deadline 的 `fetchGatewayGetResult`。反证与排除: 不存在「SSE 在 Windows 没有实现」的证据；`readiness.zig` 有 Windows socket 单测，`http_fetch.zig` 有 Windows `connectWindows` 单测。升级下载注释称每个请求有 deadline，但 `fetchTextBounded` 和 `downloadFileStreamingWithProgress` 的 `client.request(.GET, uri, .{})` 没有 deadline，`grep deadline` 在 upgrade 目录只找到 stop join budget 和该注释；Windows 的 `setRecvTimeout` 直接 return，相关唤醒测试 SkipZigTest。web fetch 的 Windows 分支有 select watch 与 TLS bundle，是独立实现，不共享 `std.http.Client` 代理。可信度: 代码证据高；真实网络 hang 为静态推断中高。

## Top 5 修复顺序

1. W-NA-08: 实现 Windows native URL opener 并修正 host capability。它直接影响 `fx login` 的三个 provider、MCP OAuth 和 Slack 安装。
2. W-NA-12: 对 `config --json` 与 profile 文件做脱敏和 Windows 凭据保护。当前有实测明文回显，且影响所有配置型凭据。
3. W-NA-13: 给 Windows 的 API key、OAuth session、subscription session 和 MCP credentials 增加 DPAPI/Credential Manager 后端与 ACL 验证。
4. W-NA-03: 接通代理初始化、`NO_PROXY`、系统代理与用户级自签 CA 策略。企业网络下这是所有联网功能的阻塞点。
5. W-NA-15: 在 `doctor` 增加 Windows 专属健康项，使代理、TLS ROOT、凭据保护、console/VT、shell、长路径、URL opener、clipboard 和 sound backend 的状态可诊断。

## 验证清单

1. 在隔离 `FX_HOME` 中只放占位凭据，运行 `fx config --json`、`fx config list`、`fx config get providers.<name>.auth.key`、`fx config set ... --json`，断言输出不含占位值。
2. 运行 `fx status --json` 与 `fx doctor --json`，断言不出现 `providers.*.auth.key` 或占位值，且 Windows check 列表包含 console/VT、shell、TLS ROOT、代理、凭据保护、长路径、URL opener、clipboard、sound。
3. 用本地代理记录连接，分别设置小写和大写 `HTTP_PROXY`/`HTTPS_PROXY`/`ALL_PROXY` 与 `NO_PROXY`，验证 HTTPS CONNECT、HTTP 绝对 URI、bypass 和代理认证。
4. 用企业 CA 与自签 CA 验证 `std.http.Client` 路径和 web fetch 路径的信任结果；不要把测试 CA 写入机器级 ROOT 当作唯一方案。
5. 在 Windows 运行 `zig build probe-http` 与一次正常交互启动，确认后台 GET 返回且首个 SSE 请求不阻塞；再用不可路由目标验证 warmup 有 deadline 或取消。
6. 用本地 silent SSE 服务验证 Ctrl+C、短 deadline、静默超过 stall window、拔网或切换网络；从 `FX_TRACE_LOG` 确认原因是 `cancelled`、`Timeout`、`stalled` 或明确网络故障。
7. 对 `fetchTextBounded` 和 `downloadFileStreamingWithProgress` 模拟无响应头、发头后静默、停止升级线程，确认 Windows 在预期时间返回且不留下线程。
8. 运行 `fx login`、`fx login codex`、`fx login grok`、MCP HTTP sign-in 和 Slack install，确认默认浏览器打开；设置 `FX_NO_OPEN_BROWSER=1` 后确认手动 URL 提示。
9. 检查 `localhost` 是否优先解析到 `::1`，分别验证 IPv4-only listener、Codex 固定端口、Slack 固定端口和随机端口回调；对固定端口占用验证错误文案。
10. 完成 `/sound` 一轮对话、trace 复制、普通文本复制、文件复制，确认 Windows 声音或 toast、剪贴板内容与失败提示。
11. 对用户新提交运行 Windows 目标单测，并补一个真实 AFD socket 的 deadline 回归；确认 `Unexpected` 只在明确 socket 上下文可重试。
