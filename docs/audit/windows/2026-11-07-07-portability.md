## 验证清单

本清单供后续修复者执行。本子代理只读审查没有运行构建或测试；主代理在当前 HEAD 的 Debug 构建实测只用于澄清正常 Windows 文件锁，不作为缺陷，也不等于构建通过结论。

1. 构建与基础 smoke：先确认后台没有 `.\zig-out\bin\fx-dev.exe`；`fx-dev.exe` 改名是开发循环设计取舍，Windows 运行中 exe 文件锁正常，残留进程需关闭后重建。再在 Windows PowerShell 执行 Debug `zig build`；主代理实测，当前 HEAD Debug 构建在后台 dev 二进制占用时仍 exit 1，`failed updating file ... to zig-out\bin\fx-dev.exe: AccessDenied`，`5/7 steps succeeded (1 failed)`；旧报告关于构建失败的部分已被实测澄清为正常文件锁，不作为产品缺陷。成功后再运行 `.\zig-out\bin\fx-dev.exe --help` 和 `.\zig-out\bin\fx-dev.exe status --json`。开发构建名以 `build.zig:101-103` 的 `fx-dev` 为准。
2. HOME 一致性：在干净 PowerShell 会话中只保留 `USERPROFILE`，临时清空 `HOME` 与 `FX_HOME`；用隔离的临时 profile 根运行 `fx status --json`、`fx usage`、`fx mcp list`，确认三者解析同一根目录。
3. MCP stdio 进程树：配置一个用 Windows shell wrapper 启动长期孙进程的 stdio MCP server；启动、调用工具、退出 fx 后，用 `Get-CimInstance Win32_Process` 按父子关系检查孙进程归零；再用 `fx mcp list` 检查重启状态。
4. 控制台关闭恢复：启动长模型请求，触发控制台关闭或注销，再启动 fx，检查 `RequestRecovery.closeActive()` 对应记录存在且终端恢复正常；headless 场景检查退出码与取消记录。
5. MCP 子服务环境：让 Windows stdio MCP server 只输出它看到的环境变量名，不输出值；检查 `SystemRoot`、`ComSpec`、`PATHEXT`、`TEMP`/`TMP`、`USERPROFILE`、`APPDATA`、`LOCALAPPDATA`、`USERNAME` 是否齐全，并断言凭据类变量不出现。
6. 网关死连接：在长 SSE 请求中禁用网卡或切换网络，记录从断网到失败的时间，与 POSIX 的 45 秒 keepalive 预算比较；确认不是等满 10 分钟 stall。
7. 持久化与权限：在临时目录中模拟 rename 后崩溃，检查 session/settings/blob 是否可恢复；用 Windows 安全描述符工具检查私有目录的 DACL，并确认宽父目录 ACL 会产生诊断或收紧。
8. 升级目标：用 Windows 构建产物执行 `fx upgrade` 或检查 target 解析，确认未发布 Windows asset 时返回明确 unsupported 文案，不请求不存在的 URL。
9. CI 守卫：在 Windows runner 上跑 `zig build`、`zig build test` 和上述 smoke；注入 W-PT-01、W-PT-03、W-PT-10 或 W-PT-14 的回归，确认检查失败，并确认 `zig build test` 跳过 suites 时有显式诊断。
10. 误报回归保护：执行 `rg -n 'std\.posix\.(poll|setsockopt|sigaction)|std\.posix\.Sigaction|supports_' src`，复核新增 `std.posix` 调用是否处在明确 Windows 剪枝域；不要把 `W-PT-15` 的命中重新判成编译失败。

## 最值得实机复现的 3 个场景

1. **stdio MCP 包装器孤儿进程**：Windows PowerShell 里配置 `npx` 或 `.cmd` wrapper 启动一个长期 MCP server，调用一次工具后关闭 fx，再观察孙进程是否仍在。这个场景直接裁决 `W-PT-01`/`W-PT-08`，也能暴露 `signal(.term)` 在 Windows 被硬杀的后果。
2. **典型 PowerShell 无 HOME 的 CLI 分裂**：在不设置 `HOME`、只设置 `USERPROFILE` 的干净会话中，分别运行 `fx status --json`、`fx usage`、`fx mcp list`。这个场景直接裁决 `W-PT-03`，并顺带观察 MCP 子服务是否因 `W-PT-04` 缺少 Windows 必需环境而启动失败。
3. **长请求期间关闭控制台**：让 fx 正在等待模型流，关闭 Windows Terminal/ConHost 窗口或触发注销，再重新打开检查请求恢复、终端代码页和 console mode。这个场景直接裁决 `W-PT-02`/`W-PT-11`，并验证在飞请求是否被当成 crash 或 clean close。
